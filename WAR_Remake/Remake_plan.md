# Modern macOS remake: plan and decisions

Decided Nov 2026.

## Decisions
- **Rewrite, not emulate.** A new program that plays like the original, using the decoded formats (see WAR_file_reference.md), the WAR.EXE disassembly (WAR_Analysis/WAR.ASM) and the OCR'd manual (WAR_Documentation/WAR_Manual_1987.pdf).
- **Language/libraries: C + SDL3**, CMake build, universal macOS app (also builds on Windows/Linux). The original is compiled C, so game logic can be ported function by function from the disassembly.
- **Assets are loaded at run time from the player's own copy** of the original game files (WAR.EXE, M, P*, O0-O8, F, CNF, T*, TITLES, DTITLES, WARET.DAT...). The remake does not ship Broderbund/Evryware graphics or campaigns.
- **CGA and VGA colour options:** the same 320x200 game screen, drawn from either the CGA asset set (4 colours, cyan/magenta/white; the scrolls in CGA palette 0, yellow/red/green) or the VGA set from WARET.DAT (16 colours, a palette per picture). Switching mode never touches game logic. 2-bit overlays (O3 font, icons, pointer) map to the nearest VGA colours of the CGA colours, except where WARET.EXE was measured to do otherwise (next point).
- **Hercules** (asked for 13 Nov, as done for At Sea): Tab's third mode (CGA, VGA, Hercules), or `HERC` on the command line as `WAR HERC`. The CGA screen is shown as WAR.EXE shows it on a Hercules card (herc_setup ovl1:8441): each 2-bit pixel as two mono pixels, 640x200 at 32,72 of a 720x348 screen (gfx.c screen_to_herc); the whole 720x348 is shown, lit pixels grey AAAAAAh as in DOSBox. Checked against DOSBox's machine=hercules (test_herc.c): the title page, the scrolls, the campaign menu and the Options Shoppe pixel for pixel; the opponents, the map and a battle apart from what moves or blinks. Comparing them found that the remake had cleared row 23 under the title page (WAR.EXE has one text row there: the picture down to line 189, a colour-3 line at 190) and left out the line under the scrolls and the Options Shoppe (lines 182-183); fixed for every mode (text_border in menu.c).
- **Video cards (asked Nov 14):** every card the original supported, as it showed the game on each: CGA, EGA, Tandy 1000, VGA, Hercules (VideoCard in gfx.h; App.card in main.c; `video=cga|ega|tandy|vga|herc` on the command line, CGA by default, `HERC` = video=herc; Tab cycles them, skipping the 16-colour three without WARET.DAT). Found by running WARET.EXE in DOSBox-X (installed Nov 14; DOSBox 0.74 agreed for WARET.EXE) as each machine and comparing pixel by pixel (WAR_Analysis/tools/dosbox egacmp.py/vgacmp.py against test/dump_cards): WARET.EXE loads a picture's palette into the DAC only on a VGA ([277E], INT 10h AX=1012h, 6-bit), so EGA and Tandy show the 16-colour pictures in the standard colours (gfx.c STD16 in screen_to_xrgb; VGA through dac6). Same indexes on all three, but: text rows colour 15 everywhere (menu.c tfg; WAR.EXE's yellow on the scrolls was wrong in the remake's VGA too); the pointer blue on EGA/VGA (bit 0 clear -> 1), ANDed as 4-bit pixels on a Tandy (and_bitmap); XOR flips 4 bits (inv = i ^ 15 in menu.c and mapedit.c); the title item 4 px left; Tandy: yellow map cursor (14) and outlines within 4 pixels (screen_sprite); Options Shoppe "EGA: sixteen colors" / "EGA: no centering", the display line skipped, black/white only on CGA. Matched pixel for pixel: opening, title page, scrolls, opponents, campaign menu, Options Shoppe, map; battle soldiers and text rows by colour (the demo's battles). Not compared yet: the battle report, the map's boxes (Info, Size, Formation), the editors. test_cards.c checks the rules.
- **Display:** 320x200 off-screen buffer, scaled to the window; options for original 4:3 aspect (pixels 1.2x taller) or square integer pixels.
- **Code location:** WAR_Remake/ in the GitHub repo. Source files carry the user's header (Opus 5.5, Brett Hallen, the Murrys, Brøderbund) and are UTF-8 with a byte-order mark (UltraEdit needs it to show the ø); new files get the same.
- **Game logic keeps WAR.EXE's units and state** (x in bytes of 4 px, y in line pairs, the shared 1000-step path memory, the enemy's 200-byte route memory, scan codes as key codes), so each C function can be checked against the routine it ports; play.c, battle.c, menu.c and the editors name the routine above each function.
- **Speed:** 20 main-loop iterations a second (estimated IBM PC/XT rate; confirmed by the user as feeling right). Time setting = iterations per tick: 64 slow (default), 16, 4, 1. Food/supply/training every 16 ticks. Map battles run every iteration. The battle screen runs at 8 frames a second (estimate). Menus and editors run at 20 Hz (the formation editor's soldiers step at 10 Hz, an estimate of WAR.EXE's loop with its picture decode).
- **Terrain is always read from the CGA map pixels**, as WAR.EXE does, even when the VGA tiles are shown.
- random() is reproduced: sum of WAR.EXE's own code words from 0BB8h, low 7 bits.
- Opponent values come from O2 (offset 277h, 19 words per opponent, copied to DS:A4DC). Their uses are in WAR_Analysis/README.md (Opponents' values); A4DE, A4E0 and A4F8 are never read by WAR.EXE.
- **Battle screen:** overlay 7 ported as a data-driven engine: O6 and O7 are loaded into one 0x2800-byte memory (O7 at +0x2000) and the original animation scripts are interpreted (triples: buffer delta dy*80+dx, sprite number via the DS:A931 table, state; 2 = blow/shot, scripts end with 101/102). Script first words are patched per background as WAR.EXE does.
- **Enemy commander:** kept in play.c (it is part of overlay 6 and shares its helpers), as the ai_ functions, with the Play fields named after their DS addresses.
- **Menus (overlay 1):** menu.c draws into its own canvas like overlay 1 draws into video memory (pictures, XOR boxes and frames, the AND-drawn pointer, text rows, icons), so leftovers show as in the original (a scroll unrolls over the previous page; in CGA it is recoloured by the palette change).
- **Data disks = folders:** SDL_GetPrefPath("AncientArtOfWar", "Remake") (macOS: ~/Library/Application Support/AncientArtOfWar/Remake/) holds CNF (options, the original's 25-byte layout), DRIVE (the name of the disk "in the drive"), F (formations, once taught) and Data Disks/<name>/, one folder per data disk (up to 12) with TITLES (first made from DTITLES), the T files and S. Files from before step 7 at the top level move into Data Disks/Data Disk 1. The disk in the drive is chosen in the Options Shoppe (the "data disk uses a:/b:" line becomes "disk <name>" / "a new data disk") and, with more than one disk, from a list ("DATA DISKS") that "( data disk )" shows (the user chose both). A floppy is copied into a new folder as it is; names are matched in any case. **Campaigns are kept in the original format** (TITLES + 1460-byte T files), so the original's campaigns can be played and changed, and the original game plays the remake's (checked in DOSBox).
- **Campaign editor (step 7):** menu.c runs the flows (rt_01A7 make/change/remove, campaign_intro, rt_02B9 with editor_menu PH, the scroll editor ovl1_6A78 for story and title with SDL text input, the rules and opponent pages reused with [A692] 6/9/10/11, write_campaign_file ovl1_7A71, write_titles ovl1_7E09, select_campaign's name shuffle). mapedit.c ports overlay 4 (O0, M tiles). sqedit.c ports overlay 3 and, like the original, draws with the game's own map (play_draw on a Play filled from the T file, every squad revealed; not play_start, which would add flags and turn spies into barbarians). The squads editor's cursor follows a held key (menu_held/menu_wants_held).
- **Formation editor (step 7):** formed.c ports overlay 5 (O8 soldiers and walking scripts, picture PL). Saved formations go to F in the remake's folder (WAR.EXE wrote F to the WAR disk) and replace the game's F at once and at every start (menu_create).
- **Saved games use the remake's own format** ("WARREMAKE-S1", sizes, the Campaign and Play structs), not the original's 217Eh-byte DS dump. A save made by a different build (struct sizes changed) is refused.
- **Original saved games are imported** (savegame.c, Nov 12): an S of 217Eh bytes is WAR.EXE's DS:8868-A9E5; each DS variable is copied into its Play field (layout in WAR_Analysis/README.md, Saved games), the campaign is rebuilt from the map, armies (9E60, the T layout), opponent and rules, and its title and story are found by matching the map against the WAR disk's and the data disk's campaigns. Not in S: random state, AAE3-AAEF (started afresh). Indices from the file are clamped. play_prepare (play.c) gives a Play with terrain and defaults for the importer. Checked with two saves made in DOSBox (one with a traced path, a mark and an encounter under way): the same screen, and play carries on.
- **App icon:** the opening title page (VGA PM / WARET record 1, else CGA), 4:3 on Apple's 824/1024 rounded square, drawn at build time from the player's files (tools/make_icon.c writes AppIcon.iconset with its own PNG writer; iconutil makes AppIcon.icns; CMake finds ../WAR_Original_Files_3.5 or WAR_GAME_DIR) and set at run time with SDL_SetWindowIcon (src/icon.c). No artwork in the repo (the user's choice).
- **DOSBox speed:** 300 cycles is about an IBM PC/XT; 1500 cycles (used for most captures) is several times faster. Constant delays (sounds) keep the same length at either speed in DOSBox (but DOSBox's lengths are 2.6x shorter than a real XT's: its calibration loop runs relatively fast); delays that are multiples of [0948] (title box, demo wait) and work without delays (scrolling) do not.
- **Reference runs of the original:** DOSBox in the container (machine=cga) with Xvfb and xdotool: /root/bin/dosrun.sh (start), doskey.sh (keys, a+b chords, sleep:N; its key holds are long enough that WAR.EXE often reads a key twice), dosshot.sh (screenshot), warword.py PAGE PARA WORD (answers the manual question from WARW; the byte is word<<4 | paragraph). For the editors: dosbox_ed.conf (war_ed, a copy with WAR.EXE patched at 336Fh to EB so the data disk can be B:, and data_b mounted as B:) and /root/bin/dosed.sh (answers the manual question by OCR, opens make changes; rerun if the OCR misreads). Screenshots in /root/dos/shots. Alt+S saves in WAR.EXE (Alt is [0549], not Ctrl). For timings record video instead: ffmpeg -f x11grab -framerate 30 -video_size 640x400 -i :99.0+192,184 (screenshots every 0.4 s alias fast blinking).
- **Claude Code (asked Nov 12):** no need to switch mid-step; Claude Code on the Mac would build and test on the real target with git directly, but the DOSBox harness and disassembly tools live in the cloud container. Plan: copy the container's scripts into the repo so a later move is easy.
- **Game log (asked Nov 13):** `--log` (normal) or `--log=verbose` / `--log verbose` on the command line; no switch during play (the user's choice). gamelog.c/h: each campaign started (begin_game, the viewer too) or saved game resumed opens a new file in the remake's folder under Logs/, named "YYYY-MM-DD HH-MM-SS <title>.log" (local time); the demo isn't logged (begin_demo closes any open log). Header: when, how, title and T file, opponent and its 19 values with their uses, seed, fight delay, squad counts, the 9 rules in the Rulebook's words with their values, a map of the cells; then the game at the start (flags, squads, the enemy's plans; verbose: the cell value, cost and supply tables). Lines carry [mm:ss tick N] (map iterations at 20 Hz, game ticks): ENEMY (ai_ functions: targets with their scores, attack flag, guarded flag, where each squad is sent and why, routes with directions and cost, attacks, flags grabbed, joins, splits, giving up a target, all out, the surrender offer), YOU (orders and answers), EVENT (sightings once per enemy squad, encounters, captures, map fights and each man lost, flags taken, terrain losses, training, tiredness, the end), BATTLE with the battle frame (setup, ground and skills, orders, each man falling, retreats, losses; Battle.frame added for it). Verbose adds the squad looked at each tick, holding ground and why, each candidate's score, the cell tables when they change, and a squads table every 16 ticks. A game's end writes the reason (result code) and the state; Alt+S keeps the log open. Logging only reads the game (macros LOGN/LOGV in play.c, blog in battle.c) and never calls random(): test_gamelog.c plays every campaign twice side by side with the same keys and battle keys, one logged and one not, and compares the Play and Battle structs byte for byte after every iteration and frame (normal and verbose; 46 battles); test_app_log.c checks main.c's handling (new file per campaign, Esc+Y reason, the demo writes none).

## Deliberate differences
- Cancelling a traced path frees its steps in the path memory (WAR.EXE leaves them in use).
- Fighting squads blink by drawing only; WAR.EXE swaps their side value every iteration (DS:9E60), which also briefly affects supply and food for them.
- Tab switches CGA/EGA/Tandy/VGA/Hercules (in WAR.EXE Tab scrolls up; the original chose by program, WAR or WARET, and Hercules at the DOS prompt with WAR HERC); F2 changes the aspect; F12 opens the asset viewer from the title page.
- Esc in play asks "Quit to the title page? (Y or N)" (no Esc in WAR.EXE). After saving, Q returns to the title page (WAR.EXE quits to DOS).
- No copy protection, no disk prompts; the data disk is a folder.
- Editors: Size never goes past 14 men (WAR.EXE lets I add more); Esc backs out of "Select the campaign you want to change." (WAR.EXE has no way back there); "No campaigns on this data disk." instead of asking for the disk; "THIS CAMPAIGN IS COMPLETE" stays 2 1/2 s; the line under the map isn't hidden beside the Size box; F is written to the remake's folder, not the WAR disk.
- The demo starts after 30 s on the title page, as the manual says (WAR.EXE: 189 turns of the blink loop, 23 s in DOSBox at 1500 cycles, about 12 s at 300 cycles, the PC/XT speed; 23 s until Nov 13, changed at the user's request); its scrolling turns run 2 1/2 times as often as other turns (measured: about 50 a second); the end of a demo game stays on screen 3 s; "One moment, please" shows 1 s. Tab and F2 don't end the demo.
- "presented by" stays until the opening tune ends (or 60000 units, 3 s, without music), as in WAR.EXE; a key skips it and stops the tune.
- Sounds are queued, not waited for: the game runs on while a beep or a tune plays, except where WAR.EXE's wait matters (the battle holds during bugle calls, the battle report shows its prompt after the tune). Keys pressed during the opening tune go through at once.
- The setting "external speaker" (Tandy/PCjr chip) is offered on any machine; WAR.EXE offers it only when INT 11h reports a PCjr-style machine.
- Accepting the opponent's surrender and the final screens wait for Enter (WAR.EXE goes straight to the battle report after a surrender).
- The battle screen runs at a fixed rate; WAR.EXE pads frames with fewer than 15 men by (28 - men) x 50 delay units, and its delay routine also calls random(), so random sequences differ.
- Archer fire chances index AB99 clamped to 0-13 (WAR.EXE can read words below the table when it runs out of targets).
- Soldier outlines are drawn per pixel in the current palette (WAR.EXE ORs/ANDs 2-bit CGA pixels with the shifted sprite).
- ai_route's open list holds up to 400 cells; WAR.EXE's holds 100 words (DS:8EAC) and would overwrite the supply map beyond that. Reads past the end of tables (route memory byte 200, flag -1) are guarded.
- WAR.EXE keeps [A512] and [A516] from the previous game; the remake starts each game with them clear.
- An imported original S keeps its marks (A51E); WAR.EXE forgets them when it loads a game.
- Options Shoppe: display "black/white" turns the whole picture grey (on a plain CGA the setting does nothing); "center the screen" is skipped by the pointer; the data disk line chooses a data disk folder; the joystick setting is stored but not used yet.
- Menu timings (title blink, frame blink, unroll speed, quote time) are chosen to look right; WAR.EXE's depend on its calibrated delay count. Measured with ffmpeg at 30 fps (Nov 2026): at 1500 cycles WAR.EXE's title box flickers about 8 times a second (0.07 s plain, 0.05 s inverted). The remake's 0.75 s / 0.65 s (approved by the user) came from an earlier, aliased measurement; delay() scales by [0948] twice for these delays, so they are slower on faster PCs.

## Open questions
- How WARET.EXE colours the shared 2bpp sprites (O3/O6/O8) in 16-colour mode.
- Exact iteration rate of the original main loop (20 Hz) and battle screen (8 Hz) are estimates. DOSBox at 1500 cycles (ffmpeg x11grab at 30 fps; sample screenshots alias): map scrolling about 50 turns a second (the whole map in about 1 s), demo ticks roughly 10-16 a second.
- Map scrolling measured at 300 cycles (the PC/XT, Nov 12, video at 30 fps): the whole map (55 steps of 2 line pairs) in about 2.8 s, 20 steps a second, the same as the remake (2.7 s). Faster PCs scrolled faster (1 s at 1500 cycles); asked the user whether to keep the XT speed.
- Driving DOSBox at 300 cycles needs keys held about 0.6 s (HOLD=0.6 for doskey.sh). Helpers added Nov 12: screentext.py (reads the text rows with the game's own 8x8 font, from font8.txt made by test/fontdump.c; replaces the OCR), dosanswer.sh, dosgo.sh (start + answer), dosplay.sh (first campaign to the map), dostime.sh, doswait.sh TEXT.
